# Agent Instructions

This repository tracks its work with **bd**, the Rust coordination engine built here. Issues live on `https://bd.quangle.net/w/bd-sync`, selected by `.bd/remote.toml`. That file contains the workspace URL and is safe to commit; access tokens are stored separately by `bd remote login` in the user's private credentials file. Do not recreate a local database or export JSONL to share issues. Use bd for all task tracking: no markdown TODO lists, no ad hoc memory files.

Run `bd prime` for current context: your claims, ready work, and project memories. Session-start hooks run it automatically in Claude Code and Copilot CLI.

## Task tracking with bd

### Core loop

```bash
bd ready                                # unblocked work, in queue order
bd show <id>                            # details, blockers, comments, lease
bd claim <id>                           # or `bd claim --next`; atomic, returns a lease token (`--token <t>` renews your own)
bd heartbeat <id> --token <t>           # renew the lease during long work (default TTL 5m)
bd close <id> --reason "what was done"  # add --failed if it failed; `bd release <id>` gives it back
```

### Recording work

```bash
bd create "Title" -d "why and what" -t task -p 2    # types: task bug feature epic chore; priority 0-4 (0 = critical)
bd create "Found while working" --dep discovered-from:<id>
bd create "Subtask" --parent <epic-id>
bd dep add <issue> <depends-on>                     # issue waits until depends-on closes
bd comment add <id> "context for whoever picks this up"
bd remember "durable project insight"               # shown by bd prime; search with bd memories <query>
```

### Rules

- Create or claim an issue before starting work, and close it when the work is done.
- Use `--json` when parsing output.
- Exit code 4 means a claim conflict: someone else holds it (another actor, or another session under your own actor name: a second `bd claim` of a live claim needs its `--token`), or it is not ready. Closing, releasing, reassigning, moving out of `in_progress` or deleting another actor's live claim fails with exit 4 naming its holder, `--force` or not (`--force` only gets past open children, blockers, dependents and unfinished runs); `--take-over` takes it over (recorded in the event history), so pass it only when you mean to. Exit code 13 means a stale `--if-revision`/`--if-status`/`--if-assignee` guard: re-read before retrying. In a remote workspace (`.bd/remote.toml`), exit code 7 means the access token (`BD_TOKEN`, or one saved by `bd remote login`) is missing or not allowed, 8 means the bd server is unreachable (the command did not take effect), and 9 means a write's answer was lost: it may have taken effect, so check (`bd show`) before running it again; `bd remote show` checks the connection and the token.
- If `bd heartbeat` fails, stop working on that issue: the claim was released, reclaimed, or taken over.
- Each agent session acts as its own actor, `<user>/<session>`, derived from the session id its harness sets (`$CLAUDE_CODE_SESSION_ID`, `$COPILOT_AGENT_SESSION_ID`, `$CODEX_THREAD_ID`) and `$BD_SESSION`; `bd prime` and `bd claim` show it. Do not set `BD_ACTOR` to a name other sessions use. If `bd prime` warns that you are the plain default actor and it holds claims, run each of your bd commands with `BD_SESSION=<name>`, and leave claims you did not take to their holder.
- After `/clear`, a resume, or in a subagent with its own session id, your earlier claims belong to another actor of your user: `bd prime` lists them under "Held by other sessions of yours" with the takeover command (`bd update <id> --assignee <you> --take-over`, which prints the new lease token to use from then on). Take one over only if this session is continuing that work. An actor named outright (`--actor`, `BD_ACTOR`) has no other sessions: other names are other actors, even under the same first segment. To hand a claimed issue to a subagent, have it take the claim over, or run its bd commands with `BD_ACTOR=<your actor>`.
- Claude Code subagents share their parent session's id, so a subagent's plain `bd` commands act as its parent. With the hooks in `.claude/settings.json` (`bd hook subagent-start`, `bd hook pre-tool-use`), a subagent is told to pass `--session agent-<id>` to every bd command, and one without it is refused with the corrected command: run that. When delegating without those hooks (or to a harness bd does not know), tell each subagent to run every bd command as `bd --session <distinct name> ...`.

### Changes

Run each change through the `change` playbook (`.bd/playbooks/change.toml`): `bd playbook run change --var task="..." --var tier=<tier>`, optionally `--parent <issue>`. Every tier has the same steps (requirements, decisions, security, implement, verify, review, score, recalibration check); the tier sets how deep each goes and adds steps. Every step closes with the evidence its acceptance criteria name. Decision records (local decisions, architecture decisions, ADRs, threat models) live in bd, in the step's design field or as `decision` issues under the step, not in repo files.

- `small` (bug fix, refactor, isolated command change): short requirements, local decisions, quick security check, self-review.
- `standard` (new command or flag, schema migration, public behavior, wire protocol, feature): detailed acceptance criteria, architecture decisions, threat assessment, independent review. `--var approval=yes` (or `bd gate create --type human` mid-run) adds a design approval for significant decisions (breaking changes, schema changes, new dependencies, a raised MSRV).
- `critical` (authentication, sign-in and tokens, server security, data migrations that can lose data, release, CI and supply chain): adds a requirements approval, ADRs, threat model, risk review, a design (architecture and security) approval and a final sign-off. Only a person resolves its human gates (`bd gate resolve`).
- The `plan-implement-review` Copilot CLI workflow covers implement, verify and review: pass it the run's review step as `reviewStep` and the run's `tier`; it files the findings it fixes as bug issues under that step and returns `confirmedFixes` (and dropped findings with their `bdId`) to close once implement and verify are closed.
- Every run ends with a score (Scoring agent work, below). Complexity is scored apart from how well the work went: estimate it at the requirements step as the run's `complexity_estimate` metadata, from the task alone; the judge scores it again at the end.
- Every 10 confirmed scores trigger a recalibration: the run's last step, `node .github/scripts/recalibrate-due.mjs --start`, counts the `change` runs with a confirmed `score` (the judge's accepted draft or a person's) and no `recalibrated` metadata, and at 10 starts the `recalibrate` playbook (`.bd/playbooks/recalibrate.toml`) over them and marks each (`recalibrated=<run>`). It reports from `calibrate.mjs` and `reviewer-catch.mjs`, proposes edits to the rubric anchors and delegation rules (a `decision` step), waits at a human gate, then applies only what was approved. Nothing is changed without that approval.

### Scoring agent work

`.bd/rubric.md` is the rubric for how well an agent did on an issue: correctness, scope, quality, verification, process and autonomy, 1 to 5 against written anchors, plus a capped overall, and the work's complexity, kept apart. A `change` run scores itself in its score step; `bd playbook run score --var issue=<id>` scores any other issue. Both run the `score-issue` Copilot CLI workflow (`.github/extensions/score-issue/`), where a judge (`gpt-6-astra` at `xhigh` effort) drafts the score into the issue's `score_judge` metadata and comments its reasoning, then traces which agents did each step, with which model and effort and for how long (`.github/scripts/trace-run.mjs`, from Copilot CLI sessions and Claude Code transcripts on this machine), into its `work` metadata. By default the draft is then accepted as the `score` metadata (`by: judge`); with `--var score_confirm=person` (a `change` run) or `--var confirm=person` (a `score` run) a person confirms or adjusts it behind a human gate, and a person may adjust an accepted score later.

### Delegating to agents

When delegating work (Agent tool, workflow `agent()` calls), pick the model and effort per task:

- Simple lookups, file searches, formatting, classification, running a command and reporting its output: smallest model (`haiku`), low effort.
- Summarizing, structured review, routine edits: mid-tier model (`sonnet`), medium effort.
- Writing or debugging non-trivial code, multi-step reasoning, verdicts that decide what ships, anything where an error is costly: strongest model (`opus`), high effort.
- Copilot names models by id: pass `model` only where a task needs a specific one (the `score-issue` judge, a `shadowReview`), otherwise let the session's model stand; the agent kind (`task`, `general-purpose`, `code-review`) and `reasoningEffort` carry the level.
- Context costs more than model choice: every request re-reads the whole conversation, so a small fix done late in a long session reads several hundred thousand tokens per request. Start a small issue in a fresh, short context (a new session, or a subagent briefed with just the issue) rather than at the end of a long one.
- If a cheaper run fails or looks uncertain, escalate a level rather than retry at the same one. Never trade correctness for cost on final outputs: a cheaper agent's "done" or "clean" is confirmed at the strongest level before it is reported.
- Change these rules, or the rubric's complexity anchors, only from evidence: `node .github/scripts/calibrate.mjs` reports every `change` run's estimate against judged complexity, its score and findings, and its cost and agent time by role, model and effort (Copilot AI credits as USD, 1 credit = $0.01, from each request's usage record; Claude Code tokens at the notional list prices in `.github/scripts/prices.json`, kept current from the claude-api skill), with time by step and by complexity band; agent time is the primary figure, elapsed time and human wait at gates are context. `node .github/scripts/reviewer-catch.mjs` reports, by complexity band, how often each reviewer model and effort catches what a paired shadow pass on the same diff and prompt found, from the review and validate agents `plan-implement-review` records in each session's `files/workflow-agents/` (Copilot keeps neither a workflow agent's prompt nor its result), and flags thin cells (under 5 pairs). For more data, run `plan-implement-review` with `shadowReview: { model, effort }` (or an array of them), which adds an unvalidated shadow reviewer to each review pass, at extra cost. The scripts' and extensions' tests run with `node --test '.github/scripts/*.spec.mjs'` (vitest-style specs over `.github/scripts/expect.mjs`, a small shim on `node:test`; `workflow-extensions.spec.mjs` runs both extensions with a stubbed SDK and a scripted agent).

`plan-implement-review` (the Copilot CLI extension `.github/extensions/plan-implement-review/extension.mjs`) runs its claim, heartbeat, setup, gate and bd-record agents as the `task` agent at low effort and escalates one that fails its schema to `general-purpose` at medium effort, once (never a same-level retry; the retry's label ends `@escalated`); planner, critic, triage and validators run as the session's model at high effort; reviewers at the session's model and effort. The caller sets the coding agents' (implement, gate fixes, review fixes) model and effort with `model` (a Copilot model id) and `effort`, chosen by the rules above. The extension also appends each review and validate agent (label, requested model and effort, a hash of its prompt, its result) to `<session folder>/files/workflow-agents/<run id>.jsonl` for `reviewer-catch.mjs`; nothing else leaves the run. `.claude/workflows/` is local to this checkout (listed in `.git/info/exclude`) and no longer maintained: the extensions and `.github/scripts/` are the workflows.

### Session completion

1. Close finished issues; create issues for remaining work.
2. When code changed, run the quality gates under Build & Test.
3. Report `git status`. Do not commit or push unless explicitly asked.

## Non-Interactive Shell Commands

**ALWAYS use non-interactive flags** with file operations to avoid hanging on confirmation prompts.

Shell commands like `cp`, `mv`, and `rm` may be aliased to include `-i` (interactive) mode on some systems, causing the agent to hang indefinitely waiting for y/n input.

**Use these forms instead:**
```bash
# Force overwrite without prompting
cp -f source dest           # NOT: cp source dest
mv -f source dest           # NOT: mv source dest
rm -f file                  # NOT: rm file

# For recursive operations
rm -rf directory            # NOT: rm -r directory
cp -rf source dest          # NOT: cp -r source dest
```

**Other commands that may prompt:**
- `scp` - use `-o BatchMode=yes` for non-interactive
- `ssh` - use `-o BatchMode=yes` to fail instead of prompting
- `apt-get` - use `-y` flag
- `brew` - use `HOMEBREW_NO_AUTO_UPDATE=1` env var

## Project: Rust `bd` coordination engine

### Build & Test

```bash
cargo build --release                 # target/release/bd
cargo test --workspace                # engine + CLI tests
cargo clippy --workspace --all-targets && cargo fmt --all
target/release/bd bench --workers 8   # throughput + invariant verification on a scratch DB
```

CI (`.github/workflows/ci.yml`) runs fmt, then clippy `-D warnings` and the tests on Linux, macOS, and Windows, plus an MSRV check, so keep all three platforms building. Releases are built by `.github/workflows/release.yml` when a `vX.Y.Z` tag is pushed; see RELEASING.md (and the `release` playbook in `.bd/playbooks/`).

### Conventions & Patterns

- Every mutation goes through `Store::write` and appends its events with `WriteCtx::emit` in the same transaction; never write SQL outside a write transaction.
- Any change that can affect readiness must call `graph::recompute` with the right seeds; `bd doctor` (`blocked_drift`) verifies against a full recompute.
- Keep the lease invariant: a lease exists iff the issue is `in_progress` and the holder equals the assignee.
- A path that ends or takes over a claim (closing, releasing, reassigning, leaving `in_progress`, deleting, importing, reclaiming inside `lease.grace`) calls `WriteCtx::check_claim_override` (or `check_claim_overrides` for several) with the operation's `take_over`, before any refusal its `force` gets past, so batches, playbooks and imports get the same answer and the first refusal names the holder. Never let a structural flag (`force`, `cascade`) or a guard (`--if-assignee`) imply a takeover. A live claim is never claimed twice without its lease token.
- Keep indexes minimal: each index is extra pages written per claim/close (see `bd bench`).
- bd plans its queries without planner statistics: a `Store` never runs `ANALYZE` or `PRAGMA optimize`, and `Store::open` drops any `sqlite_stat*` tables, so SQLite assumes every table large and every index selective (statistics taken while a workspace is young make it scan whole tables, and a long-lived connection keeps them); do not add `ANALYZE`. Queries run once per issue of a walk (recomputing a subtree, descendants, trees, blockers) also fix their plan, in case statistics appear anyway: start from the edges with `CROSS JOIN` (the left table stays the outer loop) and reach issues by id with `issues INDEXED BY sqlite_autoindex_issues_1` (see `graph.rs`). `crates/bd-core/tests/plans.rs` plans every statement the walks and single commands prepare (the walks' under stale statistics too); a statement that reads a whole table by design is listed in its `WHOLE_TABLE`.
- Playbook runs and groups are identified by `metadata.playbook.role` (`run`/`group`): they close themselves when their subtree closes; keep that metadata when touching run issues.
- Commands print and read only through `io.rs` (`outln`, `errln`, `with_stdout`, `read_input`, `send_file`), never `println!`, stdin or client-named files directly, so `bd serve` can run them in-process and capture their I/O. Admin-only operations call `io::require_admin`, machine-local ones `io::require_local`; new commands also need a class in `cli::access`.
- Overrides that depend on the caller's token (ending other actors' claims, getting past human gates) are checked in bd-core against the transaction's `Policy` (`App::write` sets it from `io::policy()`), at the point of the override, so they hold in batches and playbooks; a new override path must check it too. GitHub probes go through `gates::probe_github`, which enforces `gate.repos`.
- Agent assets: skills are code-equivalent for some harnesses (Claude Code `!` commands and `hooks`, `allowed-tools`, bundled scripts), so skills and MCP definitions are both gated: never write a new or changed skill file, a newly set executable bit, or a new or changed MCP definition without the user's approval (`bd agents approve`, which refuses agent sessions and non-terminals with no bypass); pulls, hooks and watches only report them (removals, and restores of the very bytes approved, apply). Server-provided text that reaches a terminal or an agent's context (names, fields, reasons, definitions) goes through `agents/show.rs` escaping, never printed as received.
- Session hooks print through `hook.rs` in the format of the harness that runs them, exit 0, say nothing when there is nothing to say, and keep to a time budget (`HOOK_BUDGET`, `Remote::within`).
