# Agent Instructions

This repository tracks its work with **bd**, the Rust coordination engine built here. Issues live on `https://bd.quangle.net/w/bd-sync`, selected by `.bd/remote.toml`. That file contains the workspace URL and is safe to commit; access tokens are stored separately by `bd remote login` in the user's private credentials file. Do not recreate a local database or export JSONL to share issues. Use bd for all task tracking: no markdown TODO lists, no ad hoc memory files.

Run `bd prime` for current context: your claims, ready work, and project memories. Session-start hooks run it automatically in Claude Code and Copilot CLI.

## Task tracking with bd

### Core loop

```bash
bd ready                                # unblocked work, in queue order
bd show <id>                            # details, blockers, comments, lease
bd claim <id>                           # or `bd claim --next`; atomic, returns a lease token (`--token <t>` renews your own)
bd heartbeat <id> --token <t>           # renew the lease during long work (default TTL 5m)
bd close <id> --reason "what was done"  # add --failed if it failed; `bd release <id>` gives it back
```

### Recording work

```bash
bd create "Title" -d "why and what" -t task -p 2    # types: task bug feature epic chore; priority 0-4 (0 = critical)
bd create "Found while working" --dep discovered-from:<id>
bd create "Subtask" --parent <epic-id>
bd dep add <issue> <depends-on>                     # issue waits until depends-on closes
bd comment add <id> "context for whoever picks this up"
bd remember "durable project insight"               # shown by bd prime; search with bd memories <query>
```

### Rules

- Create or claim an issue before starting work, and close it when the work is done.
- Use `--json` when parsing output.
- Exit code 4 means a claim conflict: someone else holds it (another actor, or another session under your own actor name: a second `bd claim` of a live claim needs its `--token`), or it is not ready. Closing, releasing, reassigning, moving out of `in_progress` or deleting another actor's live claim fails with exit 4 naming its holder, `--force` or not (`--force` only gets past open children, blockers, dependents and unfinished runs); `--take-over` takes it over (recorded in the event history), so pass it only when you mean to. Exit code 13 means a stale `--if-revision`/`--if-status`/`--if-assignee` guard: re-read before retrying. In a remote workspace (`.bd/remote.toml`), exit code 7 means the access token (`BD_TOKEN`, or one saved by `bd remote login`) is missing or not allowed, 8 means the bd server is unreachable (the command did not take effect), and 9 means a write's answer was lost: it may have taken effect, so check (`bd show`) before running it again; `bd remote show` checks the connection and the token.
- If `bd heartbeat` fails, stop working on that issue: the claim was released, reclaimed, or taken over.
- Each agent session acts as its own actor, `<user>/<session>`, derived from the session id its harness sets (`$CLAUDE_CODE_SESSION_ID`, `$COPILOT_AGENT_SESSION_ID`, `$CODEX_THREAD_ID`) and `$BD_SESSION`; `bd prime` and `bd claim` show it. Do not set `BD_ACTOR` to a name other sessions use. If `bd prime` warns that you are the plain default actor and it holds claims, run each of your bd commands with `BD_SESSION=<name>`, and leave claims you did not take to their holder.
- After `/clear`, a resume, or in a subagent with its own session id, your earlier claims belong to another actor of your user: `bd prime` lists them under "Held by other sessions of yours" with the takeover command (`bd update <id> --assignee <you> --take-over`, which prints the new lease token to use from then on). Take one over only if this session is continuing that work. An actor named outright (`--actor`, `BD_ACTOR`) has no other sessions: other names are other actors, even under the same first segment. To hand a claimed issue to a subagent, have it take the claim over, or run its bd commands with `BD_ACTOR=<your actor>`.
- Claude Code subagents share their parent session's id, so a subagent's plain `bd` commands act as its parent. With the hooks in `.claude/settings.json` (`bd hook subagent-start`, `bd hook pre-tool-use`), a subagent is told to pass `--session agent-<id>` to every bd command, and one without it is refused with the corrected command: run that. When delegating without those hooks (or to a harness bd does not know), tell each subagent to run every bd command as `bd --session <distinct name> ...`.

### Changes

Run each change through the `change` playbook (`.bd/source/playbooks/change.toml`, published to the workspace): `bd playbook run change --var task="..." --var tier=<tier>`, optionally `--parent <issue>`. Every tier has the same steps (requirements, decisions, security, implement, verify, review, feature spec where experimental feature specs are on, score, recalibration check); the tier sets how deep each goes and adds steps. Every step closes with the evidence its acceptance criteria name. Decision records (local decisions, architecture decisions, ADRs, threat models) live in bd, in the step's design field or as `decision` issues under the step, not in repo files.

Playbooks and skills: this repository's playbooks and agent skills are published to the workspace, not tracked as checkout copies. Their reviewed source is `.bd/source/` (`playbooks/*.toml`, `agents/claude/skills/`, `agents/codex/skills/`). To change one, edit it under `.bd/source/` and have it reviewed and merged like code, through the `change` playbook; an admin then publishes it with `bd publish --dry-run` and `bd publish`, which needs a person's admin token, and each client runs `bd agents approve` at a terminal, which agent sessions cannot do. Approval places the files in `.bd/approved/playbooks/`, `.claude/skills/` and `.agents/skills/`, which git ignores; never edit those copies in place. Until a client approves, `bd playbook run` there does not find a new playbook (it prints the approval hint) and keeps the approved version of a changed one; `bd agents status` shows what waits. Claude Code's bd skill still comes from `plugins/bd`, and `.mcp.json` stays in the repository.

- `small` (bug fix, refactor, isolated command change): short requirements, local decisions, quick security check, self-review.
- `standard` (new command or flag, schema migration, public behavior, wire protocol, feature): detailed acceptance criteria, architecture decisions, threat assessment, independent review. `--var approval=yes` (or `bd gate create --type human` mid-run) adds a design approval for significant decisions (breaking changes, schema changes, new dependencies, a raised MSRV).
- `critical` (authentication, sign-in and tokens, server security, data migrations that can lose data, release, CI and supply chain): adds a requirements approval, ADRs, threat model, risk review, a design (architecture and security) approval and a final sign-off. Only a person resolves its human gates (`bd gate resolve`).
- The `plan-implement-review` workflow (the Copilot CLI extension, or the Claude Code workflow in `.claude/workflows/`) covers implement, verify and review: pass it the run's review step as `reviewStep` and the run's `tier`; it files the findings it fixes as bug issues under that step and returns `confirmedFixes` (and dropped findings with their `bdId`) to close once implement and verify are closed. Every run has a shadow review, and the gating review runs inside the workflow so it is journaled; work done outside it is reviewed through it with `skipImplement`.
- Every run ends with a score (Scoring agent work, below). Complexity is scored apart from how well the work went: estimate it at the requirements step as the run's `complexity_estimate` metadata, from the task alone; the judge scores it again at the end.
- Every 10 confirmed scores trigger a recalibration: the run's last step, `node .github/scripts/recalibrate-due.mjs --start`, counts the `change` runs with a confirmed `score` (the judge's accepted draft or a person's) and no `recalibrated` metadata, and at 10 starts the `recalibrate` playbook (`.bd/source/playbooks/recalibrate.toml`) over them and marks each (`recalibrated=<run>`). It reports from `calibrate.mjs` and `reviewer-catch.mjs`, proposes edits to the rubric anchors and delegation rules (a `decision` step), waits at a human gate, then applies only what was approved. Nothing is changed without that approval.

### Feature specs

Feature specs are an experimental feature, on in a workspace with `bd config set experimental.features specs` (`bd prime` then shows a "Feature specs" section with the open specs and the work left unlinked; turning them on records `experimental.specs.since`): every `bd spec` command refuses where it is off, and the `change` playbook leaves out its spec step (`condition = "{{experimental.specs}}"`). A feature's canonical requirements, what it does and deliberately does not do, live in bd beside the work that shaped them, so they can be read without digging through closed issues. A spec is a pinned `feature` issue labelled `spec` and `area:<name>`; each requirement is a pinned child `story` labelled `requirement` (plus `non-goal` for a non-behavior), one testable sentence, linked to the issue or run it came from (an outgoing `related` edge). Pinned keeps them out of `bd ready`. Write them with the `bd spec` commands, which check the targets and write nothing when a check fails (options before `--`; the raw `bd create`, `bd supersede` and `bd close` forms are equivalent): `bd spec new <area> -- '<feature>'` creates a spec (`--parent <spec>` for a sub-spec), `bd spec add <spec> --from <id> -- '<sentence>'` a requirement (`--non-goal` for a non-goal). A requirement in force stays pinned; one that changes is replaced with `bd spec change <old> --from <id> -- '<sentence>'` (a new requirement superseding the old); one that no longer holds is closed with `bd spec remove <old> -r '<why>'`. Specs nest: a sub-feature's spec is a direct child of its feature's spec and inherits its requirements, so a rule shared by sub-features lives once on the parent, and a sub-spec never contradicts its parent (supersede the parent's requirement instead). bd refuses to close or supersede a spec while any child is open, so to retire a feature, close its whole subtree deepest first (requirements, then their spec); to replace one, move its sub-specs and the requirements that still hold to the new spec (`bd update <id> --parent <new>`), supersede or close the rest, then supersede the old spec (`bd supersede <old spec> --with <new spec>`). An open spec under a closed one is therefore always a mistake (`--force`, or a reopen: bd-9373): `bd spec show` still prints it, inheriting nothing, with an error naming the fixes (and `bd spec drift` lists it as orphaned). Any other issue (an epic, say) between two specs ends inheritance, with a warning. An area may hold several specs. Every change closed while specs are on is linked to the spec(s) it touches: a `related` edge from its issue (or its run) to the spec or requirement (`bd spec link <issue> <spec or requirement>`, or `bd dep add <issue> <spec or requirement> --type related`; a link covers the issue's subtree and its ancestors), or `bd spec none <issue> -r '<why>'` for work with no user-visible behavior (covering that issue only). A requirement's sources are its own outgoing `related` edges. Playbook runs, steps and everything below a step, gates, decisions, ephemeral issues, work closed as failed and work closed with `bd duplicate`/`bd supersede` need no link. `bd spec list` lists the open specs; `bd spec show <area | spec id>` prints the area's specs (or one spec) as Markdown, sub-specs nested beneath their spec and, for the specs printed at the top, the requirements inherited from the specs above (`--history` adds superseded and removed requirements, `--json` an array of views, each nested view with its full `inherited`); `bd spec drift` reports work closed since `experimental.specs.since` and not linked, requirements whose source reopened or failed, specs and requirements neither pinned nor closed, and orphaned specs (exit 1 when there are any); `bd spec candidates` groups the closed work from before then that specs could be written from. The `spec-bootstrap` playbook (`.bd/source/playbooks/spec-bootstrap.toml`) drafts specs for named candidate groups, one agent step per group in turn, behind a human review gate (`--var reviewer=<person>`). `bd doctor` warns when specs are off but open specs remain. The `change` playbook's spec step keeps them current.

### Scoring agent work

`.bd/rubric.md` is the rubric for how well an agent did on an issue: correctness, scope, quality, verification, process and autonomy, 1 to 5 against written anchors, plus a capped overall, and the work's complexity, kept apart. A `change` run scores itself in its score step; `bd playbook run score --var issue=<id>` scores any other issue. Both run the `score-issue` workflow (the Copilot CLI extension `.github/extensions/score-issue/`, judge `gpt-6-astra` at `xhigh` effort, or the Claude Code workflow `.claude/workflows/score-issue.js`, judge `fable` at high effort), where the judge drafts the score into the issue's `score_judge` metadata and comments its reasoning, then traces which agents did each step, with which model and effort and for how long (`.github/scripts/trace-run.mjs`, from Copilot CLI sessions and Claude Code transcripts on this machine), into its `work` metadata. By default the draft is then accepted as the `score` metadata (`by: judge`); with `--var score_confirm=person` (a `change` run) or `--var confirm=person` (a `score` run) a person confirms or adjusts it behind a human gate, and a person may adjust an accepted score later. About one `change` run in eight is started with `--var score_confirm=person`, so the judge's gap from a person can be measured: those whose task issue id (the `--parent`, else the task text) has a SHA-1 starting 0 or 1 (`printf %s <id> | sha1sum | cut -c1`), so the choice can't be cherry-picked.

### Delegating to agents

When delegating work (Agent tool, workflow `agent()` calls), pick the model and effort per task:

- Simple lookups, file searches, formatting, classification, running a command and reporting its output: smallest model (`haiku`), low effort.
- Summarizing, structured extraction, routine edits: mid-tier model (`sonnet`), medium effort.
- Writing or debugging non-trivial code, multi-step reasoning, verdicts that decide what ships, anything where an error is costly: strongest model (`opus`), high effort.
- Review that gates a change (the `change` review step, `plan-implement-review`'s reviewers and validators): the strongest class (`opus`), never `haiku`; medium effort at complexity 3 or below, high at 4-5 (the run's estimate until it is judged). Both workflows run their reviewers at the session's model, at `reviewEffort` when given, else the session's effort (validators at high): the controller passes `reviewEffort: high` for a run estimated at 4-5, and runs on the strongest class; a session on a smaller model hands the review to one that is. A `sonnet` review pass is a calibration shadow, not the gate. The evidence, provisional until bd-sync's own pairs fill the cells: the `calibrate-delegation` skill.
- In Claude Code, name models by class (`haiku`, `sonnet`, `opus`), never by versioned ID, so each level tracks the latest model of its class; Fable is used only as the Claude Code `score-issue` judge (named `fable`).
- Start every subagent description (Agent tool) with its role and a colon: `coder:`, `reviewer:`, `mechanical:`, `research:`, `planner:` or `summary:` (`coder: bd spec drift`, `reviewer: review r1 bd-x.1`), so `calibrate.mjs` can cost each role instead of counting it as other; workflow `agent()` labels already name theirs.
- Copilot names models by id: pass `model` only where a task needs a specific one (the `score-issue` judge, a `shadowReview`), otherwise let the session's model stand; the agent kind (`task`, `general-purpose`, `code-review`) and `reasoningEffort` carry the level.
- Context costs more than model choice: every request re-reads the whole conversation, so a small fix done late in a long session reads several hundred thousand tokens per request. Start a small issue in a fresh, short context (a new session, or a subagent briefed with just the issue) rather than at the end of a long one.
- If a cheaper run fails or looks uncertain, escalate a level rather than retry at the same one. Never trade correctness for cost on final outputs: a cheaper agent's "done" or "clean" is confirmed at the strongest level before it is reported.
- Subagents (Agent tool, and a workflow's own `agent()` calls) have no Workflow tool, so in Claude Code only the top-level session can run `plan-implement-review` or `score-issue`. To work through several `change` runs, that session is the controller and runs the workflows itself:
  1. Per issue, start the run. A subagent briefed with just the issue and run id (`planner:`, `opus`) does the requirements, decisions and security steps and the complexity estimate, but no coding.
  2. The controller starts `plan-implement-review` in the background for each run (`issue`, the run's review step as `reviewStep`, `tier`, `actor`, `shadowReview`, `model`/`effort`, `plannerEffort` for a planner effort exploration pick, `logDir`, the session's scratchpad). It covers implement, verify and review, so reviews are journaled for `reviewer-catch.mjs`.
  3. Keep at most about 4 runs going at once: more concurrent cargo builds and test runs (each worktree builds its own `target/`, a cold build) overload the machine and cause timing flakes.
  4. As each workflow finishes, the controller merges its worktree, then runs the quality gates on the main checkout in its own `target/` (CARGO_TARGET_DIR unset, e.g. `env -u CARGO_TARGET_DIR cargo test --workspace`), never with `target/implement-review` or a worktree's target, before it closes the steps and findings and runs `score-issue`. A subagent it hands the merge and closing to is described `mechanical:` (`mechanical: close bd-x.1`), not `coder:`: it is not the run's coder.
  5. End the controller session after about 10 finished runs (merged, closed and scored) or at the end of the batch, whichever comes first, and continue the batch in a fresh session: every request rereads the whole context. In squi a controller grown to 1000+ requests was the largest cost line (its main thread, about $1062 of $4.9k notional); bd-sync's longest controller so far worked through about 13 runs in 315 requests at a flat ~170k tokens per request (a fresh session starts near 140-150k), its main thread about $24 notional, about a tenth of those runs' cost, so ending it sooner would save little and lose the workflows it runs. Recheck the number from evidence (calibrate.mjs's Controller sessions section: each controller session's main thread, its cost and tokens read per request by quarter, against the runs it traced and finished) when these rules are recalibrated. To hand off, start no new workflow and let the running ones finish (a background workflow belongs to the session that started it), finish step 4 for those you can, then add a bd comment to each unfinished run with its state: run id, step reached, worktree path, branch, logDir and what is left (merge, close steps and findings, `score-issue`, or `plan-implement-review` not yet started, with its args). The comment holds no tokens, lease tokens or credentials. The next session finds these runs with `bd ready` and the runs' comments, and resumes from them.

  Never have subagents write code and then gate it with a plain-subagent review. Code a subagent has already written still goes through `plan-implement-review` with `skipImplement`.
- Coder exploration quota: about one eligible run in four runs its coding agents (`plan-implement-review`'s `model` and `effort`) on the mid-tier class (`sonnet`, or Copilot's matching id) at medium effort, so the report can show where the strongest class is needed for coding. Eligible: tier `small`, complexity estimate 2 or less, and no change to commands, flags, output or JSON shapes, exit codes, the wire protocol, MCP tools, the schema, or authorization and token code. A run is chosen when the first hex digit of its id's SHA-1 is 0-3 (`printf %s <run> | sha1sum | cut -c1`), so the choice can't be cherry-picked; record it before implement with `bd update <run> --set-metadata 'exploration={"coder":"sonnet/medium","rule":"sha1-0-3"}'` and say so in the implement comment. Review still gates it on the strongest class (above), and a failed gate escalates the coding a level per the rule above. `calibrate.mjs`'s Score by coder section compares these runs with the others.
- Planner effort exploration: about one eligible run in four runs `plan-implement-review`'s planner, critic and triage agents at medium effort (`plannerEffort: 'medium'`) instead of high, so the report can show where high-effort planning is needed; validators stay high, and the pre-step planner subagent (step 1 above), briefed the same way for every run, is not part of it. Eligible: tier `small` and a complexity estimate of 3 or below; an eligible run is picked when the second hex digit of its id's SHA-1 is 0-3 (`printf %s <run> | sha1sum | cut -c2`), independent of the coder pick's first digit, so a run can carry both. A run that is not eligible or not picked runs at the default high and gets no record. The planner's model stays the session's, and review still gates it on the strongest class at the usual effort (above). Record it before implement with `bd update <run> --set-metadata 'exploration={"planner":"opus/medium","plannerRule":"sha1-2-0-3"}'` (in Copilot, the session's model id in place of `opus`); set-metadata replaces the whole `exploration` value, so for a run the coder quota also picked, write both pairs in one object (`{"coder":"sonnet/medium","rule":"sha1-0-3","planner":"opus/medium","plannerRule":"sha1-2-0-3"}`), and say so in the implement comment. `calibrate.mjs`'s Score by planner section compares these runs with the others.
- Change these rules, or the rubric's complexity anchors, only from evidence (the `calibrate-delegation` skill gathers it): `node .github/scripts/calibrate.mjs` reports every `change` run's estimate against judged complexity, its score and findings, and its cost and agent time by role, model and effort (Copilot AI credits as USD, 1 credit = $0.01, from each request's usage record; Claude Code tokens at the notional list prices in `.github/scripts/prices.json`, kept current from the claude-api skill), with time by step and by complexity band; agent time is the primary figure, elapsed time and human wait at gates are context. `node .github/scripts/reviewer-catch.mjs` reports, by complexity band and rubric version, how often each reviewer model and effort catches what a paired shadow pass on the same diff and prompt found, from the review and validate agents the Copilot extension records in each session's `files/workflow-agents/` (Copilot keeps neither a workflow agent's prompt nor its result), the Claude Code workflow's journals on this machine, and `reviewer:` subagents paired with a shadow by identical prompt, and flags thin cells (under 5 pairs). The Copilot extension gathers that data by default: each review pass also runs every reviewer as an unvalidated shadow at `claude-sonnet-5.5` medium and `claude-opus-5.5` high, at extra cost; `shadowReview: { model, effort }` (or an array of them) picks other shadows, `shadowReview: false` none; the Claude Code workflow runs a shadow only when given `shadowReview`, which the `change` playbook requires. The scripts', extensions' and Claude Code workflows' tests run with `node --test '.github/scripts/*.spec.mjs'` (vitest-style specs over `.github/scripts/expect.mjs`, a small shim on `node:test`; `workflow-extensions.spec.mjs` runs both extensions with a stubbed SDK and a scripted agent; `suite-lock.spec.mjs` covers the suite lock; `workflows-meta.spec.mjs` and `plan-implement-review.*.spec.mjs` lift helpers out of `.claude/workflows/` and keep each workflow's listed description within the skill listing's budget).

`plan-implement-review` (the Copilot CLI extension `.github/extensions/plan-implement-review/extension.mjs`) runs its claim, heartbeat, setup, gate and bd-record agents as the `task` agent at low effort and escalates one that fails its schema to `general-purpose` at medium effort, once (never a same-level retry; the retry's label ends `@escalated`), and so does the `score-issue` extension (`.github/extensions/score-issue/extension.mjs`) with its setup, trace and record agents; planner, critic, triage and validators run as the session's model at high effort; reviewers at the session's model, at `reviewEffort` when given, else the session's effort. The caller sets the coding agents' (implement, gate fixes, review fixes) model and effort with `model` (a Copilot model id) and `effort`, chosen by the rules above. The extension also appends each review and validate agent (label, requested model and effort, a hash of its prompt, its result) to `<session folder>/files/workflow-agents/<run id>.jsonl` for `reviewer-catch.mjs`; nothing else leaves the run. The Claude Code workflows in `.claude/workflows/` are maintained beside the extensions, on the same engine: mechanical agents (claim, heartbeat, setup, gates, trace and bd records, in both workflows) on `haiku` at low effort, escalated once to `sonnet` at medium (`@sonnet`); planner, critic, triage and validators at high effort; reviewers at the session's model, at `reviewEffort` when given, else the session's effort; every cargo command with `CARGO_TARGET_DIR=<the worktree>/target` (a target dir per worktree: checkouts of one workspace sharing a target dir get the same fingerprint per workspace crate and judge freshness by mtimes, so one could link another's build). In both harnesses each agent writes its command output to its own file, `<logDir>/<run>/<label>.log` (default `<TMPDIR>/plan-implement-review`; `<run>` is the issue id made safe for a path, or `run-<hash>` without one; reviewers use `mktemp` files, so real and shadow prompts stay identical); the gate's log starts with a `bd-gate: dir=... run=...` marker, and a marker naming another directory or run, or a pass without one, is escalated once and then ends the run as escalated with 'gate log contaminated', instead of passing or reaching the gate-fix coder; a retry after an uncontaminated report-only failure may reuse the first attempt's complete log for the same tree instead of rerunning the suite; a full `cargo test --workspace` from a workflow worktree runs through `node .github/scripts/suite-lock.mjs --run <run> -- cargo test --workspace --locked`, which serializes full suites across worktrees with a lock at `<git common dir>/bd-suite.lock` and exits 75 when it is still busy after 180 s (nothing ran: rerun the command), while fmt, clippy and `cargo test -p` run without it. Their per-argument notes live in a comment at the top of each script, because the skill listing cuts `whenToUse` at about 1,500 characters; read it before passing arguments beyond the listed ones. A change to one workflow's behavior is made in both harnesses' versions.

### Session completion

1. Close finished issues; create issues for remaining work.
2. When code changed, run the quality gates under Build & Test.
3. Report `git status`. Do not push unless explicitly asked.

## Non-Interactive Shell Commands

**ALWAYS use non-interactive flags** with file operations to avoid hanging on confirmation prompts.

Shell commands like `cp`, `mv`, and `rm` may be aliased to include `-i` (interactive) mode on some systems, causing the agent to hang indefinitely waiting for y/n input.

**Use these forms instead:**
```bash
# Force overwrite without prompting
cp -f source dest           # NOT: cp source dest
mv -f source dest           # NOT: mv source dest
rm -f file                  # NOT: rm file

# For recursive operations
rm -rf directory            # NOT: rm -r directory
cp -rf source dest          # NOT: cp -r source dest
```

**Other commands that may prompt:**
- `scp` - use `-o BatchMode=yes` for non-interactive
- `ssh` - use `-o BatchMode=yes` to fail instead of prompting
- `apt-get` - use `-y` flag
- `brew` - use `HOMEBREW_NO_AUTO_UPDATE=1` env var

## Project: Rust `bd` coordination engine

### Build & Test

```bash
cargo build --release                 # target/release/bd
cargo test --workspace                # engine + CLI tests
cargo clippy --workspace --all-targets && cargo fmt --all
target/release/bd bench --workers 8   # throughput + invariant verification on a scratch DB
```

The web UI (`web/`, SvelteKit, npm) has its own checks, run in `web/`: `npm ci && npm run check && npm run lint && npm run format:check && npm run build` (see `web/AGENTS.md`, which also covers its Svelte AI tooling).

CI (`.github/workflows/ci.yml`) runs fmt, then clippy `-D warnings` and the tests on Linux, macOS, and Windows, plus an MSRV check, so keep all three platforms building. Releases are built by `.github/workflows/release.yml` when a `vX.Y.Z` tag is pushed; see RELEASING.md (and the `release` playbook in `.bd/source/playbooks/`).

### Architecture Overview

Rust re-implementation of beads as a coordination engine on SQLite WAL (see README.md; user documentation lives in `docs/`, contributor notes in CONTRIBUTING.md: update the page a change affects).

Each crate's file-by-file guide is in its own `AGENTS.md`. Claude Code loads one when a file in that directory is read; in another harness, read it before changing the crate.

- `crates/bd-core` (library): the engine, from storage, the issue lifecycle, claims and the graph to playbooks, gates and agent assets. File by file: `crates/bd-core/AGENTS.md`.
- `crates/bd-cli` (library `bd-cli`: the commands, which `bd serve` runs too): the CLI grammar, the commands, MCP and the remote client. File by file: `crates/bd-cli/AGENTS.md`.
- `crates/bd-server` (library `bd-server`: `bd serve`, over `bd-cli`'s commands): the server, access tokens, sign-in, browser approvals and the MCP endpoint. File by file: `crates/bd-server/AGENTS.md`.
- `.claude-plugin/marketplace.json` lists the Claude Code plugin `plugins/bd` (`.claude-plugin/plugin.json`, `hooks/hooks.json` equal to `.claude/settings.json`'s hooks, `skills/bd/SKILL.md`), next to the Copilot CLI plugin `.copilot-plugin/plugin.json`, which `.github/plugin/marketplace.json` lists for Copilot CLI (it reads that file before `.claude-plugin/marketplace.json`); `hook.rs` tests keep them in step.
- `crates/bd` (binary `bd`): `main.rs` gives `bd-cli` its `Handler` (`bd serve` from `bd-server`, `bd bench`); `bench.rs` is the throughput and invariant harness; `tests/cli.rs` and `tests/remote.rs` run the binary end to end (`tests/remote.rs` real `bd serve` and client processes).

### Conventions & Patterns

- Every mutation goes through `Store::write` and appends its events with `WriteCtx::emit` in the same transaction; never write SQL outside a write transaction.
- Any change that can affect readiness must call `graph::recompute` with the right seeds; `bd doctor` (`blocked_drift`) verifies against a full recompute.
- Keep the lease invariant: a lease exists iff the issue is `in_progress` and the holder equals the assignee.
- A path that ends or takes over a claim (closing, releasing, reassigning, leaving `in_progress`, deleting, importing, reclaiming inside `lease.grace`) calls `WriteCtx::check_claim_override` (or `check_claim_overrides` for several) with the operation's `take_over`, before any refusal its `force` gets past, so batches, playbooks and imports get the same answer and the first refusal names the holder. Never let a structural flag (`force`, `cascade`) or a guard (`--if-assignee`) imply a takeover. A live claim is never claimed twice without its lease token.
- Keep indexes minimal: each index is extra pages written per claim/close (see `bd bench`).
- bd plans its queries without planner statistics: a `Store` never runs `ANALYZE` or `PRAGMA optimize`, and `Store::open` drops any `sqlite_stat*` tables, so SQLite assumes every table large and every index selective (statistics taken while a workspace is young make it scan whole tables, and a long-lived connection keeps them); do not add `ANALYZE`. Queries run once per issue of a walk (recomputing a subtree, descendants, trees, blockers) also fix their plan, in case statistics appear anyway: start from the edges with `CROSS JOIN` (the left table stays the outer loop) and reach issues by id with `issues INDEXED BY sqlite_autoindex_issues_1` (see `graph.rs`). `crates/bd-core/tests/plans.rs` plans every statement the walks and single commands prepare (the walks' under stale statistics too); a statement that reads a whole table by design is listed in its `WHOLE_TABLE`.
- Playbook runs and groups are identified by `metadata.playbook.role` (`run`/`group`): they close themselves when their subtree closes; keep that metadata when touching run issues.
- Commands print and read only through `io.rs` (`outln`, `errln`, `with_stdout`, `read_input`, `send_file`), never `println!`, stdin or client-named files directly, so `bd serve` can run them in-process and capture their I/O. Admin-only operations call `io::require_admin` (`io::require_admin_human` where only a person may: `bd publish`), machine-local ones `io::require_local`; new commands also need a class in `cli::access`.
- Overrides that depend on the caller's token (ending other actors' claims, getting past human gates) are checked in bd-core against the transaction's `Policy` (`App::write` sets it from `io::policy()`), at the point of the override, so they hold in batches and playbooks; a new override path must check it too. GitHub probes go through `gates::probe_github`, which enforces `gate.repos`.
- Agent assets: skills are code-equivalent for some harnesses (Claude Code `!` commands and `hooks`, `allowed-tools`, bundled scripts), so skills and MCP definitions are both gated, and so are a remote workspace's playbooks: never write a new or changed skill file, a newly set executable bit, a new or changed MCP definition, or a new or changed approved playbook without the user's approval (`bd agents approve`, which refuses agent sessions and non-terminals with no bypass); pulls, hooks and watches only report them (removals, and restores of the very bytes approved, apply). A remote client runs only playbooks found on it (checkout, approved, user's own) and always sends them as a bundle; never fall back to the server's own copy (the MCP endpoint, with no client, is the documented exception). Server-provided text that reaches a terminal or an agent's context (names, fields, reasons, definitions) goes through `agents/show.rs` escaping, never printed as received.
- Session hooks print through `hook.rs` in the format of the harness that runs them, exit 0, say nothing when there is nothing to say, and keep to a time budget (`HOOK_BUDGET`, `Remote::within`).
