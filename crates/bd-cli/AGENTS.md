# `crates/bd-cli`

The file-by-file guide to this crate, kept apart from the root `AGENTS.md` so it loads only when working here. Update it when a change affects what it says. The root `AGENTS.md` applies here too, its Conventions & Patterns above all.

- `crates/bd-cli` (library `bd-cli`: the commands, which `bd serve` runs too; `lib.rs` holds `run`, `execute` and `dispatch`, and hands `bd serve` and `bd bench` to the binary through `set_handler`): clap grammar in `cli/` (`mod.rs`: `Cli`, `Global`, `Command`; one file per command group); mutations are `exec_*` functions over `WriteCtx` in `commands/` (one file per area: issues, links, claims, memory, config, workspace, events, prime, health, transfer, views, edit (`bd edit`: one field in `$VISUAL`/`$EDITOR`, written back under the revision read); shared argument helpers in `mod.rs`, with `write_output` for client-named output files: `io::send_file` under `bd serve`, else a temp file and `io::replace_file`) so `batch.rs` can run them in one transaction; `cli/specs.rs` and `commands/specs.rs` hold `bd spec` (`list`, `show`, `drift`, `candidates`, `changes` read; `none`, `new`, `add`, `change`, `remove`, `link` write, `exec_spec_*`, also in batches); `cli/views.rs` and `commands/views.rs` hold the reporting views (`bd query`, `bd epic`, `bd children`, `bd stale`, `bd orphans`, `bd graph`); `graph_view.rs` renders a `Subgraph` as a text tree, Graphviz DOT or a self-contained HTML page (inline SVG, no script, a CSP meta), every title through `io::printable` and escaped for its format; `actor.rs` resolves who a command acts as (`--actor`, `$BD_ACTOR`, else the user, as `<user>/<session>` in an agent session; a session hook takes the session id from its JSON input where the harness keeps it from hook processes) and implements `bd hook session-start` (also syncing agent assets via `agents/hook.rs`), `subagent-start` and `pre-tool-use` (Claude Code hooks giving sessions and subagents their own actor); `hook.rs` prints session hook context in each harness's format (plain text for Claude Code and Codex, one `{"additionalContext"}` object for Copilot CLI), reads the hook's stdin input once (its `cwd` is the session's directory), tells which harness runs a hook (`runs_in`) and whether it runs after compaction (`compacted`: SessionStart with source `compact`, which Claude Code and Codex run again, so `bd hook session-start` says so in a workspace and `bd prime` restores the context; PreCompact/PostCompact output never reaches the model); `agents.rs` implements `bd agents` (`manifest`/`fetch` read the workspace's sets, or with `--playbooks` its playbooks; `status`, `pull`, `approve` and `watch` are client-side, intercepted in `remote::forward`, and check every server answer before writing; in a remote workspace they include the server's playbooks whatever `--harness`, and with no harness work on them alone) with `agents/checkout.rs` (the checkout, skill files and approved playbooks (`.bd/approved/playbooks`) never written through symlinks, the OS-locked `.bd/agents.lock.mutex`), `lock.rs` (`.bd/agents.lock`, with the approved playbooks' hashes under `playbooks`, left out while empty), `approved.rs` (a remote workspace's playbooks on the client: status/pull (removals, restores of the bytes approved, strays removed), `apply_approved`, and `verify_bundle`, which checks a bundle's approved files against the lock and keeps their path references inside the approved directory before it is sent), `mcp_file.rs` (native MCP files; `.codex/config.toml` via `toml_edit`), `sync.rs` (the status/pull engine, `apply_approved`), `approve.rs`, `show.rs` (escaping server-provided text), `hook.rs` (the session-start sync, within `HOOK_BUDGET`), `session_hook.rs` (the harness's session-start hook a pull adds where none is configured: bd's own entries, never the server's; shared with `bd setup`: hook kinds `BdHook`, `Entry` lists per event (`session_entries`, `claude_project_entries` = this repository's `.claude/settings.json` hooks), presence per event over `Sources` (`All` for pull, `TargetAndPlugins` for `bd setup claude`, installed Claude Code plugins found in `<claude home>/plugins/cache`), `ensure_entries`/`remove_entries` returning an `Outcome` (pull's `HookReport` plus the events), removal of exactly bd's commands) and `watch.rs`; `setup.rs` (with `cli/setup.rs`) implements `bd setup <harness>` (machine-local, never forwarded): hooks for claude/codex/copilot through `session_hook`, a marked Markdown section (`setup::section`) for cursor/gemini/opencode; the project root is the nearest ancestor holding a `.bd` directory or a `.git` entry, whichever is closer (a nested worktree is set up in itself), and the checkout mutex is taken only when `agents::find_checkout` resolves to that root's `.bd`; `backup.rs` holds the backups `bd backup` (a local workspace, refused in a remote one) and `bd serve`'s backup job take (`Store::snapshot` copies named `<dir>/<name>/<name>-<UTC>.db`, keep-N retention, private directories; `take_with` for `server.db`); `mcp/` implements `bd mcp` and the JSON-RPC that `bd serve`'s MCP endpoint (`bd-server`'s `mcp_http.rs`) shares: `tools.rs` (the tool catalog: strict argument validation, each call built into a CLI command line with `--flag=value` and `--`, compact results), `mod.rs` (JSON-RPC for MCP `2026-07-28` (stateless, `_meta`) and `2025-11-25` (an `initialize` session for the rest of the process), behind a `Runner` trait), `local.rs` (runs a call in-process via `execute` with captured I/O and a token-less `Policy`), `stdio.rs` (the stdio loop, the per-process actor, forwarding to `bd serve` in a remote workspace); `gh.rs` runs `gh` for gates and `bd github` (one binary, `$BD_GH`, one timeout, one cancellation flag that `bd serve`'s shutdown trips; `gh api --include` parsing, pagination links, rate limits); `github.rs` implements `bd github status/pull/push/sync` (snapshot, fetch, plan, GitHub writes, then one write transaction; a `GithubApi` trait so tests use a fake); `gate_review.rs` implements `bd gate review` (`Access::Local`: `people_only` refuses agent sessions, then a stdin that is not a terminal; the loop `review` over a `Gates` trait, `LocalGates` over the `App` (one `resolve_gate` write per gate, never forced) and `RemoteGates` over a `Remote` sending the keychain token (only `info`, `gate list`, `gate show` and `gate resolve`, parsed by pure functions), each gate read again (kind, phase, approvers) before `Resolve <id>? [y/N]` on stderr; `summary_text` and the JSON `Summary` on stdout; `one_line` escapes an error's message to one line, keeping its variant and exit code); `playbooks.rs` and `gates.rs` implement `bd playbook` and `bd gate` (GitHub gates shell out to `gh`, outside any write transaction; approval links through `gates::approval_url_of`, for open human gates that are armed or escalated, in `bd gate show` (with its run, `part of`) and `gate list --json`, `bd prime` and `bd playbook status`; in a remote workspace `playbooks.rs` looks a name up in the checkout's `.bd/playbooks`, then the server's approved on this machine, then the user's own, and always sends what it loads with the command as a bundle (verified by `agents::approved::verify_bundle`), behind the hidden `--playbook-bundle` flag, so the server compiles the approved bytes, never its own copy (a bundle's `server_first` is still read for older clients); a name found nowhere fails with the approval hint; with the workspace's `playbooks.source = server` (`config::PlaybooksSource`, asked of the server by `client_source` (one `config get`, parsed strictly by `source_answer`, anything else or a failure is off) only where `lookup` says it changes the answer: some by-name reference of the bundle built on the whole path, the command line's or a nested `extends`/`expand`, resolved in the checkout or the user's paths; a file path on the command line is never asked about) the bundle is rebuilt without the checkout, one escaped warning per checkout copy skipped (`warn_ignored`), and a name it resolved outside the approved that the server's manifest serves (`refuse_served_unapproved`, names compared ignoring ASCII case by `served_name`; a failed manifest read fails closed, `manifest_unread`) is not found; `list` asks only when the checkout holds playbooks or a user playbook has a name the server serves unapproved, marks them `Mark::Ignored`/`Mark::Unavailable`, and reports `"source"` when it asked; with `bd prime` it sends a `Listing` of the checkout's, the approved and the user's playbooks (shadowed ones too; the server keeps the first of each name, and with `playbooks.source = server`, which it reads itself, leaves the checkout's out, counted in `ForPrime::ignored`) and the hashes approved, behind the hidden `--client-playbooks` flag, which the server lists in place of its own, naming its playbooks waiting for approval (an older client's bare array still reads; under bd serve its disk loaders are `Loader::contained`); `publish.rs` (with `cli/publish.rs`) implements `bd publish` over bd-core's `publish` (`io::require_admin_human`: under bd serve an admin token of kind human; the source `.bd/source` or `--from`, read into a bundle on the client and sent in a remote workspace behind the hidden `--publish-bundle` flag (`attach_bundle`, called from `remote::forward`, which also turns an older server's refusal of the flag into an upgrade message), never read from the server's disk; dry runs with bounded unified diffs; one server log line per publish or refusal). Remote workspaces, on the client: `remote/` (`config.rs` (`--remote`/`BD_REMOTE`/`.bd/remote.toml`, `Trust`, the token sent), `client.rs` (retries with request ids; `Remote::within` puts every request and retry under one deadline for hooks), `delivery.rs` (stdout and output files of an answer), `forward.rs` (`remote::run` runs `bd gate review` on the client before anything is forwarded), `events.rs` (`poll_events` long-polls events by op), `renew.rs` (`Remote::access_token` renews a saved sign-in token when due or refused, under `credentials.lock`, in the credentials file or the keychain (`Place`), a keychain entry re-read under the lock used only if its CA trust still passes against the Remote's `Trust`; revocation), `human.rs` (the person's keychain token for one command: `human_remote` checks no agent session and a terminal before opening the keychain (5 s), then the URL's item, its CA trust and whether its kind and role cover the refusal's `needs`; `forward` retries a write-free `needs` refusal once with it under a new request id, `bd publish` takes it up front, `detect_for` when no other token is configured, and `bd gate review` always (`detect_for`'s `review_remote`: `gate_review::people_only`, the remote configuration, then `human_remote` once, never `token_for`, every error through `gate_review::one_line`; `person_error` turns a skip into its refusal, exit 2 or 7); never read for anything else), `cmd.rs` (`bd remote`; `login/logout/show --human`)), `credentials.rs` (tokens saved per server by `bd remote login`, mode 0600; sign-in ones marked `signed_in`, with their refresh token; changed under `credentials.lock`), `keychain.rs` (a person's token (kind human) kept by `bd remote login --human` in the OS keychain only, one JSON `HumanEntry` per item (service `bd`, account `server:<key>` or `workspace:<key>`): a `HumanStore` per OS (Secret Service over D-Bus, the macOS login Keychain, Windows Credential Manager; none elsewhere, no file fallback; a file fake under `BD_TEST_KEYCHAIN` in debug builds), run by `Bounded` on one worker thread in order with a timeout that poisons it, writes carrying the `credentials.lock` handle (`Held`) so a timed-out write keeps the lock until it ends), `protocol.rs` (wire format), `stream.rs` (the client's reader of streamed answers), `tokens.rs` (`Role`, `Kind`, the summary line of a token, `random_hex`), `io.rs` (stdio and files, or a request's capture; under `bd serve`, the summary of the request's token and `Capture.approvals`, the base `<issuer>/w/<ws>/gates/` of the approval pages it offers the request, which `io::approval_url(id)` turns into a link for ids `approval_id_ok` accepts, None outside such a capture; `Capture.operation_links` (`OperationLinks`: base `<issuer>/w/<ws>/`, workspace, the link key, a `Debug` hiding it) and the opaque `Capture.operation`, which `note_operation` fills (only where links are offered; a blank reason is none, any other kept byte for byte) and `operation_link()` seals when the error is printed), `approval_link.rs` (operation approval links: `Op` (close, discard), `OperationRequest` {workspace, op, issue, reason, failed, force, requester, at, until = at + 7 days} in a strict length-prefixed binary encoding, sealed with ChaCha20-Poly1305 (`LinkKey`, 32 bytes, no `Debug`) under AAD `bd-op:v1:<ws>:<op>:<issue>` into hand-rolled unpadded base64url (`seal`, `open` → `Opened::{Invalid, Expired, Valid}`, input over `MAX_TOKEN` refused before decoding; `MAX_REASON` 2000 bytes, `Unsealable::ReasonTooLong`; `MAX_QUERY` 8 KiB); `note_close`/`note_discard`, called from the `bd close` dispatch closure and `cmd_discard` on an approvable error, note the request only for one id with `--force` and no `--take-over` (close) or without `--take-over`/`--dry-run` (discard), so batches and other commands never get a link; `render_error` prints `approve the close of <id> in a browser: <url>` (or `the discard of`, or `no browser approval link for ...: <why>`) after the gate's line and adds `error.operation_approval_url` to JSON; `mcp/mod.rs`'s `CARRIED_ERROR_KEYS` (`gate`, `approval_url`, `operation_approval_url`) carry them into MCP tool errors).
